The `winget-app-install.ps1` script is designed to be self-healing: it repairs corrupt sources, auto-installs missing modules, retries failed installs, and elevates itself when needed — all without prompting. Most problems resolve on their own. When they do not, the sections below explain exactly what is happening and how to fix it.

<Accordion title="Script fails with 'Access Denied' or does not start">

The script requires **Administrator privileges** to install packages system-wide.

**What the script does automatically:** When you run the script without elevation, it detects the non-elevated context and relaunches itself in an elevated session without asking. If Windows Terminal is installed, it opens in a new elevated Windows Terminal tab. Otherwise it falls back to a standard elevated PowerShell window. You will see a UAC consent dialog during the relaunch. This works for one-liner (`irm | iex`) runs too: the script re-downloads itself to a temp file so there is a local copy to relaunch.

**If the UAC prompt is suppressed** by Group Policy, contact your system administrator to allow standard users to consent to elevation, or ask an administrator to run the script directly. Under remote execution where elevation is unavailable, the script exits with code 1 rather than hanging on a dialog nobody can see.

</Accordion>

<Accordion title="Winget source corruption — error code 0x8a15000f">

Error `0x8a15000f` means the local winget source cache is corrupted or contains missing data. The script detects this automatically by running a test search against the `winget` source and checking for the corruption error pattern.

**What the script does automatically:**
1. Runs `winget source reset --force` to wipe and re-register the default sources.
2. Re-registers the source package from the Microsoft CDN: `Add-AppxPackage -Path 'https://cdn.winget.microsoft.com/cache/source.msix'`
3. Retries the source check. If the source is healthy, installation continues without any further action on your part.

**If the auto-repair fails**, run the repair manually in a **non-elevated** PowerShell session (source package registration is per-user and must run as the standard user, not as Administrator):

```powershell
# Run as your normal user account (not elevated):
Add-AppxPackage -Path "https://cdn.winget.microsoft.com/cache/source.msix"
```

Then verify the source is functional:

```powershell
winget source list
winget search 7zip --source winget
```

If the search returns results without error, the source is healthy and you can re-run the install script.

</Accordion>

<Accordion title="Winget repair fails with a downgrade rejection — error code 0x80073D06">

Error `0x80073D06` (`ERROR_INSTALL_PACKAGE_DOWNGRADE`) means AppX rejected a framework dependency (Microsoft.WindowsAppRuntime, VCLibs, or UI.Xaml) because the machine already has a **newer** build than the one the WinGet release pins — routine on a managed fleet where Teams, Phone Link, or an MDM push updates one of those independently. `-Force` cannot fix this; it only makes the repair more insistent about deploying the older pinned build, so it fails the same way every time.

**What the script does automatically:**
1. Before attempting any repair, it tries registering the App Installer (winget) MSIX package that is already staged on the machine for the current account — no download, no framework dependency deployment, so the downgrade rejection cannot occur. This is the common case when you elevated as a different admin account than the interactive user, since App Installer registration is per-user.
2. If that does not resolve it, the script runs `Repair-WinGetPackageManager -Latest` unforced, then `-Force` if the unforced attempt fails for a different reason.
3. If a `-Force` attempt is rejected with `0x80073D06`, the script stops immediately instead of retrying — this is a WinGet packaging conflict, not a fault on your machine, and retrying only burns another multi-hundred-megabyte download before failing the same way.

**If you hit this error**, winget is likely already functional for whichever account has it registered — try running the install script as (or elevating from) that account instead of a separate admin account. If no account on the machine has a working winget, downgrade the newer framework package manually before retrying, or wait for a WinGet release that pins a matching or newer version.

</Accordion>

<Accordion title="Pre-flight check failures">

Before installing anything, the script validates three system requirements. A failure in any of them stops or warns the installation.

**OS Version check (warning, non-blocking)**

The script checks that your Windows build is 19044 or higher (Windows 10 21H2); Windows 11 builds are recognised as supported. Older builds display a warning but do not block the install. Upgrade Windows to ensure full winget compatibility:

```powershell
# Check your current build:
[System.Environment]::OSVersion.Version.Build
```

**Disk space check (warning, non-blocking)**

The script recommends at least **50 GB free on the C: drive**. If less is available — or free space cannot be measured — it warns and proceeds; nothing prompts. To check free space:

```powershell
Get-PSDrive -Name C | Select-Object -Property Used, Free
```

**Network check (blocking)**

The script tests connectivity to `cdn.winget.microsoft.com:443`. If this check fails, the script exits because winget cannot download packages without network access.

Verify connectivity:

```powershell
Test-NetConnection -ComputerName cdn.winget.microsoft.com -Port 443
```

If the connection fails, check that:
- Your network interface is active.
- A firewall or proxy is not blocking outbound HTTPS traffic to `cdn.winget.microsoft.com`.
- You are not on a restricted corporate network that requires a proxy configuration.

To bypass pre-flight checks entirely (for automated or headless scenarios):

```powershell
.\winget-app-install.ps1 -SkipSystemCheck
```

</Accordion>

<Accordion title="Individual app install fails">

When an individual package fails to install, the script automatically **retries it once** before reporting the failure in the summary table.

**What the script does automatically:**
1. Attempts the installation using `winget install -e --accept-source-agreements --accept-package-agreements --source winget --id <package>`.
2. Verifies the install succeeded by running `winget list --exact --id <package>`.
3. After all packages have been processed, any that failed are collected and retried once before the final summary is produced.

**Manual retry:** If an app still shows as `Failed` in the summary, re-run the script — it skips already-installed packages and only attempts the failed ones again.

To install a specific package manually and verify:

```powershell
winget install -e --accept-source-agreements --accept-package-agreements --source winget --id <PackageId>
winget list --exact --id <PackageId>
```

Check the winget source is healthy first if the error mentions missing manifests or hash mismatches:

```powershell
winget source list
winget source reset --force
```

</Accordion>

<Accordion title="Microsoft.WinGet.Client module missing">

The `Microsoft.WinGet.Client` PowerShell module provides richer update detection and package management than the raw `winget` CLI. The script uses it when available and falls back to CLI commands when it is not.

**What the script does automatically:** On each run, the script checks for `Microsoft.WinGet.Client` via `Get-Module -ListAvailable`. If it is missing, the script installs it from the PowerShell Gallery (including the NuGet provider if needed):

```powershell
Install-Module -Name Microsoft.WinGet.Client -Scope AllUsers -Force -AllowClobber
```

**If the automatic install fails**, install the module manually in an elevated PowerShell session:

```powershell
# Ensure NuGet provider is present:
Install-PackageProvider -Name NuGet -MinimumVersion 2.8.5.201 -Force -Scope AllUsers

# Install the module:
Install-Module -Name Microsoft.WinGet.Client -Scope AllUsers -Force -AllowClobber

# Verify:
Get-Module -ListAvailable -Name Microsoft.WinGet.Client
```

<Note>
The script functions correctly without `Microsoft.WinGet.Client` — it uses `winget` CLI commands as a fallback. You only lose the richer update detection and `Update-WinGetPackage` integration.
</Note>

</Accordion>

<Accordion title="Automatic updates (Winget-AutoUpdate) not running">

Ongoing updates are handled by [Winget-AutoUpdate (WAU)](https://github.com/Romanitho/Winget-AutoUpdate), which the install script sets up automatically — see [Automatic Updates](/winget/scheduled-updates). If installed apps are not staying current, check the WAU scheduled task.

**Task details:**

| Property | Value |
|----------|-------|
| Task name | `Winget-AutoUpdate` |
| Task path | `\WAU\` |
| Schedule | Weekly at 2:00 AM |
| Runs as | SYSTEM (machine-wide), plus a user-context pass |

**Check task status:**

```powershell
Get-ScheduledTask -TaskName "Winget-AutoUpdate" -TaskPath "\WAU\"
Get-ScheduledTaskInfo -TaskName "Winget-AutoUpdate" -TaskPath "\WAU\"
```

**Common reasons updates are not applying:**
- The machine is off or asleep at the scheduled time — the task runs at the next opportunity.
- WAU is not installed (e.g. it was removed manually). Re-run `winget-app-install.ps1` — it reinstalls the pinned WAU version whenever it is missing or outdated.
- A specific app is excluded by WAU's include/exclude lists — see the [WAU documentation](https://github.com/Romanitho/Winget-AutoUpdate) for its configuration and log locations.

<Note>
Older versions of the installer used a per-user task named `WingetAppSetup-ScheduledUpdates` with `-EnableScheduledUpdates`/`-DisableScheduledUpdates` flags. That feature was removed; the flags no longer exist, and the uninstall script cleans up any legacy task it finds.
</Note>

</Accordion>
